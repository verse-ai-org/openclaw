## 简介
本文件系统性阐述 OpenClaw 的认证体系，覆盖连接认证、凭据管理、令牌验证与多因素（多因素：在当前代码库中未发现专门的"多因素认证"实现，但支持多种凭据来源与组合使用，可视为广义的多因子策略）认证支持。**最新更新**包括认证提供者组系统的重大重组，增强了PROVIDER_EMOJI、PROVIDER_LOGO和PROVIDER_MODEL_CANDIDATES映射，移除了多个提供者条目，简化了架构。同时，增加了对OAuth设备代码流的重大增强，包括设备代码流支持、PKCE安全机制、CSRF保护等新特性，以及MiniMax认证系统的模型标识符更新。内容包括认证流程、凭据存储、认证策略与安全传输机制；并提供认证配置选项、凭据轮换与故障排除建议，以及安全配置最佳实践。

## 项目结构
OpenClaw 的认证能力由以下模块协同实现：
- 网关层认证：解析与校验请求头中的令牌或密码，支持受信任代理与 Tailscale 身份识别。
- 浏览器端认证：对浏览器请求进行 Bearer 令牌与 Basic 密码校验。
- 凭据管理：提供 OAuth、API Key、Token、设备代码等凭据类型与存储路径。
- 安全工具：定时安全比较函数，防止时序攻击。
- 秘钥运行时：集中解析与激活 SecretRef 引用，统一凭据表面。
- 插件 SDK：在 HTTP 请求中自动附加 Bearer 令牌并处理鉴权失败重试。
- 设备代码流认证：支持OAuth设备代码流，提供安全的用户授权机制。
- **认证提供者组系统**：重构后的提供者分类与元数据管理，支持emoji、logo和模型候选映射。
- **MiniMax认证系统**：支持M2.5和M2.7模型族的OAuth认证，包括高速推理变体。

## 核心组件
- 网关认证与模式选择
  - 支持模式：无认证、令牌、密码、受信任代理、默认令牌。
  - 模式来源：显式覆盖、配置、密码存在、令牌存在、默认。
  - 受信任代理：从指定头部提取用户身份，支持白名单用户与必选头部。
  - Tailscale：通过代理转发头与 WhoIS 校验实现免密登录。
- 浏览器请求认证
  - 支持 Bearer 令牌与 Basic 密码，使用安全比较函数避免时序攻击。
  - 允许通过自定义头部传递密码作为补充校验。
- 凭据管理与存储
  - 支持 OAuth、API Key、Token、设备代码等凭据类型。
  - 存储位置：按 Agent 隔离，支持迁移与兼容文件。
  - 多账户/多配置：通过 profileId 与 auth.order 实现路由。
  - 设备代码认证：支持MiniMax等提供商的设备代码流认证。
- 秘钥运行时与 SecretRef
  - 统一解析 env/file/exec 等来源的凭据引用，激活到运行时快照。
  - 对未激活的引用发出警告，便于诊断。
- 插件 SDK 的 Bearer 自动注入
  - 在 HTTP 请求中自动附加 Bearer，并在 401/403 时按作用域回退获取新令牌。
- 设备代码流认证
  - 实现OAuth设备代码流（RFC 8628），支持用户代码输入授权。
  - 集成PKCE安全机制，提供证明密钥交换保护。
  - 包含CSRF保护，验证状态参数的一致性。
- **认证提供者组系统**
  - 重构后的提供者分类与元数据管理，支持emoji、logo和模型候选映射。
  - 移除了多个不再使用的提供者条目，简化了架构。
  - 增强了PROVIDER_EMOJI、PROVIDER_LOGO和PROVIDER_MODEL_CANDIDATES映射。
- **MiniMax认证系统**
  - 支持M2.5和M2.7模型族的OAuth认证，包括基础版和高速推理变体。
  - 提供M2.7 Lightning模型的特殊定价支持。
  - 统一的模型定义和别名管理。

## 详细组件分析

### 网关认证与模式选择
- 模式解析
  - 优先级：显式覆盖 > 配置 > 密码存在 > 令牌存在 > 默认令牌。
  - 受信任代理模式需提供 userHeader 与可信代理列表。
  - Tailscale 模式在非本地直连且允许时，通过代理头与 WhoIS 校验用户身份。
- 授权流程
  - 受信任代理：校验必选头部与用户白名单。
  - 令牌模式：要求 Authorization 头为 Bearer 且与配置一致。
  - 密码模式：支持自定义头部或 Basic 密码，均使用安全比较。
  - 速率限制：对错误尝试进行限流，成功后重置。
- 启动时认证生成
  - 在特定模式下不会自动生成令牌，以确保明确的凭据来源。

## OAuth设备代码流

### 设备代码流概述
OpenClaw 实现了完整的 OAuth 设备代码流（RFC 8628），为无法使用传统重定向回调的场景提供安全的用户授权机制。该流程适用于移动设备、智能电视或其他没有浏览器环境的设备。

### 设备代码流工作原理
设备代码流分为两个主要阶段：

## PKCE安全机制

### PKCE概述
Proof Key for Code Exchange (PKCE) 是 OAuth 2.0 的安全扩展，专门用于保护授权码流程中的客户端凭证。在设备代码流中，PKCE 提供了额外的安全层，防止授权码拦截攻击。

### PKCE工作机制
PKCE 通过以下三个组件实现安全保护：

1. **verifier（证明者）**：高熵随机字符串，客户端持有
2. **challenge（挑战）**：verifier的SHA-256哈希，base64url编码，发送给授权服务器
3. **state（状态）**：随机值，用于CSRF保护

```mermaid
flowchart TD
V["生成verifier<br/>(32字节base64url)"] --> C["计算challenge<br/>SHA-256(verifier)"]
C --> S["生成state<br/>(16字节base64url)"]
V --> R["发送challenge和state<br/>到授权服务器"]
R --> T["授权服务器验证<br/>code_verifier"]
T --> OK["授权成功"]
```

**图表来源**
- [oauth-utils.ts:19-24](file://apps/electron/src/main/oauth-utils.ts#L19-L24)

### PKCE在设备代码流中的应用
在设备代码流中，PKCE通过以下方式增强安全性：

- **挑战-响应验证**：确保授权码只能由原始客户端兑换
- **防止中间人攻击**：即使授权码被截获，没有verifier也无法兑换
- **CSRF保护**：state参数防止跨站请求伪造

## CSRF保护机制

### CSRF威胁概述
跨站请求伪造（CSRF）是一种常见的Web安全攻击，攻击者诱使用户在已认证的网站上执行非预期操作。在OAuth流程中，CSRF攻击可能导致恶意用户获得访问令牌。

### CSRF防护策略
OpenClaw 采用多重CSRF防护机制：

1. **随机state参数**：每次授权请求生成唯一state值
2. **state回显验证**：授权服务器必须在回调中返回相同的state
3. **会话状态管理**：在服务器端存储期望的state值

```mermaid
sequenceDiagram
participant C as "客户端"
participant AS as "授权服务器"
C->>AS : "请求授权<br/>state=RANDOM"
AS-->>C : "返回授权页面<br/>state=RANDOM"
C->>AS : "用户授权回调<br/>state=RANDOM"
AS->>AS : "验证state一致性"
AS-->>C : "返回授权码"
```

### CSRF防护实现细节
- **state生成**：使用16字节随机数生成base64url编码的状态值
- **state验证**：在授权回调时严格验证state参数的一致性
- **错误处理**：state不匹配时拒绝授权并记录潜在的CSRF攻击

## 故障排除指南
- "未找到凭据"
  - 确认已通过向导或命令写入对应 provider 的凭据。
  - 对于 Anthropic setup-token，需在网关主机上执行相应命令并粘贴。
- "令牌即将过期/已过期"
  - 使用健康检查命令确认具体过期 profile。
  - 重新登录或更新令牌，必要时清理过期条目。
- "受信任代理未配置/用户缺失"
  - 检查上游代理是否正确设置转发头与 userHeader。
  - 确认允许的用户列表包含当前用户。
- "Tailscale 用户不匹配"
  - 检查代理是否正确透传用户头。
  - 确保 WhoIS 查询返回的用户与请求头一致。
- "HTTPS 要求"
  - 插件 SDK 可强制要求 HTTPS，若目标站点不支持请调整配置。
- **设备代码流相关问题**
  - 状态不匹配：检查CSRF state参数是否正确传递和验证。
  - 设备代码过期：设备代码通常有5-10分钟有效期，需要及时完成授权。
  - 轮询超时：如果轮询超过设备代码有效期，需要重新开始授权流程。
  - PKCE验证失败：确保code_verifier与code_challenge正确对应。
  - 提供商特定错误：如MiniMax的2013错误，检查必需参数是否完整。
- **认证提供者组系统相关问题**
  - **提供者未显示**：检查认证提供者组定义文件是否正确同步。
  - **emoji或logo不显示**：确认PROVIDER_EMOJI和PROVIDER_LOGO映射是否正确配置。
  - **模型候选不正确**：验证PROVIDER_MODEL_CANDIDATES映射是否包含正确的模型列表。
- **MiniMax认证相关问题**
  - **模型ID错误**：确认使用的模型ID格式正确（MiniMax-M2.5/M2.7）。
  - **默认模型不匹配**：检查配置中的默认模型是否符合预期。
  - **高速模型不可用**：确认对应的高速推理变体是否已正确配置。
  - **M2.7 Lightning模型**：确认Lightning变体的特殊配置要求。

## 结论
OpenClaw 的认证系统以"最小暴露面、强安全基线、可运维性"为目标，提供多模式认证、细粒度凭据管理与安全传输保障。**最新增强**包括OAuth设备代码流支持、PKCE安全机制、CSRF保护，以及认证提供者组系统的重大重组。通过增强的PROVIDER_EMOJI、PROVIDER_LOGO和PROVIDER_MODEL_CANDIDATES映射，简化了架构并提高了用户体验。通过 SecretRef 统一解析、运行时快照、速率限制、设备代码流、认证提供者组系统和MiniMax认证系统等机制，既满足复杂场景下的灵活配置，又保持了较低的维护成本与较高的安全性。
